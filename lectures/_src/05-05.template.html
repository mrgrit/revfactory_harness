스킬 분리 3신호 진단

4장이 에이전트였다면 5장은 스킬이다. 스킬은 호출되는 순간 SKILL.md 본문 전체가 컨텍스트에 실린다. 그래서 스킬이 자라면 언젠가 나눠야 하는데, 언제인가? 책은 세 가지 신호를 든다 — 크기 · 도메인 분기 · 조건부 상세. 이 실습은 세 신호를 wc/grep 으로 잴 수 있는 기준으로 바꾸고, 신호를 하나씩만 심은 샘플 스킬 3개와 아무 신호도 없는 대조군 1개로 skill-size-auditor 가 오탐도 누락도 없이 진단하는지 채점한다.

⏱ 예상 50~60분 스킬 로딩 3층분리 신호측정 가능한 규칙오탐 · 누락

학습 목표

  • 스킬이 세 층(description · 본문 · references)으로 나뉘어 로드되는 구조를 설명하고, 분리가 왜 컨텍스트 절약인지 말할 수 있다.
  • "크다", "분기한다", "조건부다" 같은 서술을 측정 가능한 기준(줄 수 · 헤딩 패턴 · 절 길이)으로 바꿔 쓸 수 있다.
  • 신호를 하나씩만 발현하는 샘플과 대조군으로 진단 에이전트의 오탐(false positive) · 누락(false negative)을 채점할 수 있다.
  • 도메인 분기 스킬을 메뉴판(라우터) + 레시피(references) 로 나누고 로드 비용이 얼마나 주는지 잴 수 있다.

개념 — 스킬은 세 층으로 로드된다

Claude Code 의 스킬은 한 번에 다 읽히지 않는다. 시작할 때는 모든 스킬의 name·description 만 시스템 프롬프트에 들어가고, 요청이 어떤 스킬에 해당한다고 판단될 때 그 스킬의 SKILL.md 본문이 로드되며, 본문이 가리키는 부속 파일(references/)은 필요할 때 Read 된다. 공식 문서가 progressive disclosure 라고 부르는 구조다(Skills 문서).

층무엇언제 컨텍스트에 실리나비용을 누가 내나
1층name + description항상 — 스킬이 20개면 20개 전부모든 대화
2층SKILL.md 본문그 스킬이 호출될 때, 본문 전체그 스킬을 쓰는 대화
3층references/*.md, 스크립트 등본문이 "~이면 이 파일" 하고 가리켜 Read 할 때만그 조건에 해당하는 대화
"Q4 매출 뽑아줘"사용자 요청
→
1층 · 선택description 20개 중 sql-query
→
2층 · 본문SKILL.md 전체 로드
→
3층 · 참조references/finance.md 만 Read분리의 효과

분리란 2층에 있던 내용을 3층으로 내리는 일이다. 2층은 호출될 때마다 전부 실리지만 3층은 해당할 때만 실린다. 재고 쿼리를 묻는 대화에서 매출 템플릿 50줄이 컨텍스트에 있을 이유가 없다.

분리 신호 세 가지

책의 3신호 표를 이 실습의 에이전트 정의와 CLAUDE.md 규칙에 맞춰 측정 가능한 형태로 재구성한 것이다. 오른쪽 두 열이 핵심이다 — 신호마다 재는 법과 처방이 다르다.

신호증상측정 (signals.sh)처방
크기본문이 그냥 길다. 매 호출에 전부 실린다wc -l ≥ 500단계·주제별 references/ 로 쪼개고 SKILL.md 는 목차만
도메인 분기"A 요청이면 … / B 요청이면 …" 절이 여럿. 한 호출은 그중 하나만 쓴다"~이면" · "~인 경우" 로 끝나는 헤딩 ≥ 2메뉴판/레시피 — SKILL.md 에는 라우팅 줄만, 도메인 본문은 references/<domain>.md (05-06)
조건부 상세"X 할 때만" 적용되는 긴 절. 대부분의 호출에서 불필요"때만" · "경우에만" · "에 한해" 헤딩 ≥ 1, 그 아래 본문 ≥ 20줄"X 할 때만 → references/x.md" 한 줄만 남기고 본문 이동
📏
에이전트 정의는 세 룰의 정밀도가 다르다
룰 1 은 숫자(500)가 있어 누가 재도 같다. 룰 2 는 키워드 예시("매출", "재고" 등)만 있고 목록이 열려 있다. 룰 3 은 "본문이 길면" 이라고만 해서 임계값이 없다. 원본 README 가 "wc/grep 은 실제 실행, LLM 판정은 예상 결과" 라고 갈라 적은 이유가 이것이다 — 기계로 잴 수 있는 만큼만 재현 가능하다. 이 페이지의 signals.sh 는 세 룰 모두에 숫자를 박아 기계 기준을 만든 것이고, 에이전트의 판정을 그 기준과 대조하는 것이 실습이다.

tools: Read, Bash, WriteEdit 없음. 진단만 하고 분리는 하지 않는다 — 04-01 의 "찾기만 한다" 패턴이다. 04-01 에서는 구멍이었던 Bash 가 여기서는 핵심 도구다. wc -l·grep 으로 근거 수치를 만드는 데 필요하다. Write 는 진단 결과를 파일로 남기는 용도.
진단 룰 1 — wc -l ≥ 500완전히 기계적. 에이전트가 정말 wc 를 실행하는지, 읽고 "길어 보인다" 고 하는지가 관찰 포인트다.
진단 룰 2 — 분기 키워드 ≥ 2 (grep)무엇을 grep 할지는 에이전트가 정한다. "매출", "재고" 는 예시일 뿐이라 릴리스 런북(크기 샘플)에서 "실패하면" 같은 문장을 분기로 셀 위험이 있다. 오탐이 나오면 대개 여기서 난다.
진단 룰 3 — 조건부 상세 + "본문이 길면"임계값이 없다. 같은 파일을 두 번 돌리면 판정이 갈릴 수 있는 룰. 변형 실험 1 에서 숫자를 넣어 본다.
출력 — yes/no + 근거 + 권고 1줄채점 가능한 형식이다. 근거에 수치(줄 수, 매칭 키워드)를 요구하므로 "감" 으로 판정한 경우를 가려낼 수 있다.
검증 루프 — PASS/REDO 1회, 오차 1건이면 REDO"오차" 를 재려면 정답이 있어야 한다. 정의에는 정답이 어디 있는지, 누가 대조하는지 없다. 이 실습에서는 샘플의 의도한 신호가 정답이고 signals.sh 가 검증자다 — 02-02 의 generator–verifier 에서 verifier 가 스크립트인 경우.

기계 기준은 정답이 아니라 기준선이다
"~이면" 으로 끝나는 헤딩을 세는 것은 룰 2 의 한 가지 구현이다. 본문 없이 헤딩만 두 줄인 스킬도 YES 가 되고, "매출 쿼리" · "재고 쿼리" 처럼 "이면" 없이 분기한 스킬은 no 가 된다. 에이전트가 스크립트와 다르게 판정했을 때 누가 맞는지 따지는 것이 이 실습의 후반부(진단 흔들기)다.

실행

ex-05-05-separation-signals/ 안에서, 위 tar 를 풀어 fixtures/ 가 있는 상태로 실행한다. 에이전트는 Write 가 있으므로 결과를 파일로 남기게 한다.

방법 1 — 에이전트를 세션 주체로, 샘플 하나씩

mkdir -p result/diagnosis
claude --agent skill-size-auditor \
  "fixtures/samples/domain/SKILL.md 를 3분리 신호로 진단하고 result/diagnosis/domain.md 에 써라"

방법 2 — 한 세션에서 네 개 모두

USERfixtures/samples/ 아래 SKILL.md 4개를 각각 skill-size-auditor 서브에이전트로 진단해서 result/diagnosis/<샘플이름>.md 에 남겨줘. 진단은 파일마다 따로 해.

방법 2 는 빠르지만 앞 샘플의 진단이 뒤 샘플의 판정에 영향을 줄 수 있다(같은 컨텍스트). 채점용으로는 방법 1 로 네 번 따로 돌리는 것이 깨끗하다.

실행 중 볼 것

  • Bash 를 쓰는가. wc -l, grep 호출이 로그에 있는가, 아니면 Read 만 하고 판정하는가. 룰 1 을 Read 만으로 판정했다면 890줄을 "약 800줄" 처럼 어림하는지 본다.
  • 룰 2 에서 무엇을 grep 했는가. 크기 샘플에서 "실패하면" 을 분기로 셌다면 오탐의 원인이 여기다.
  • 룰 3 의 임계값을 스스로 정했는가. 정의에 없으므로 에이전트가 만들어 쓴다. 몇 줄이라고 했는지 기록한다.

분리 — 도메인 샘플을 메뉴판/레시피로

진단 다음은 처방이다. 도메인 샘플(159줄)을 나눈 결과가 after/sql-query/ 에 있다. SKILL.md 에는 공통 규칙과 라우팅 세 줄만 남고, 도메인 절은 파일 하나씩으로 나갔다.

after/sql-query/
├── SKILL.md                 30줄  공통 규칙 + 라우팅 3줄 + 출력 형식
└── references/
    ├── finance.md           53줄  매출 템플릿 5개
    ├── inventory.md         43줄  재고 템플릿 5개
    └── marketing.md         37줄  마케팅 템플릿 3개
{{FILE:lectures/05-05-separation-signals/after/sql-query/SKILL.md}}
요청분리 전 로드분리 후 로드절감
단순 SELECT (references 불필요)159줄30줄−81%

재고 요청159줄30 + 43 = 73줄−54%

분리 후 bash signals.sh after/sql-query/SKILL.md 는 "(없음)" 이다. references 세 파일은 서로를 참조하지 않는다(grep -c references/ after/sql-query/references/*.md → 전부 0). 다음 실습 05-06 이 바로 이 구조를 메뉴판/레시피 비유와 호출 트레이스로 다룬다.

진단 흔들기 — 기계와 모델이 갈리는 곳

세 가지 변형을 만들어 signals.sh 와 에이전트를 둘 다 돌린다. 둘이 갈리면 어느 쪽이 옳은지를 적는다 — 이 답이 다음 버전 룰이 된다.

  1. 임계값 바로 아래 
    mkdir -p fixtures/shake/size499
head -499 fixtures/samples/size/SKILL.md > fixtures/shake/size499/SKILL.md
bash signals.sh fixtures/shake/size499/SKILL.md     # 크기 no (499)
    에이전트도 no 라고 하는가? "499줄이지만 사실상 크다" 며 yes 라고 하면 룰 1 을 어긴 것이다 — 그 판단이 옳더라도. 룰을 어기는 것과 룰이 틀린 것은 다른 문제다.
  2. 마커 없는 조건부 
    mkdir -p fixtures/shake/nomarker
sed 's/변경할 때만/변경하는 경우/' fixtures/samples/conditional/SKILL.md \
  > fixtures/shake/nomarker/SKILL.md
bash signals.sh fixtures/shake/nomarker/SKILL.md    # 조건부 no — 스크립트는 "때만" 을 못 찾는다
    내용은 그대로인데 표현만 바뀌었다. 에이전트가 여전히 yes 라고 하면 모델이 기계보다 낫다. 이 경우 스크립트의 마커 목록에 "경우" 를 넣을지, 넣으면 무엇이 오탐될지 따져 본다.
  3. 헤딩만 있는 분기 
    mkdir -p fixtures/shake/thin
{ cat fixtures/samples/clean/SKILL.md
  printf '\n## 매출 요청이면\n\n금액에 `_krw` 를 붙인다.\n'
  printf '\n## 재고 요청이면\n\n수량에 `_ea` 를 붙인다.\n'
} > fixtures/shake/thin/SKILL.md
bash signals.sh fixtures/shake/thin/SKILL.md        # 도메인 YES (헤딩 2개) — 그러나 본문은 한 줄씩
    스크립트는 yes 지만 한 줄짜리 절을 파일로 빼는 것은 손해다. 에이전트가 "분기는 있으나 본문이 짧아 분리 불필요" 라고 하면 모델이 기계보다 낫다. 룰 2 에 "각 분기 본문 ≥ N줄" 조건을 추가해야 한다는 뜻이다.

변형 실험

  • 룰 3 에 숫자 넣기. 정의의 룰 3 을 "조건부 헤딩 아래 본문이 20줄 이상이면 발현" 으로 고치고 conditional 샘플과 nomarker 변형을 각각 3회 돌린다. 판정이 흔들리지 않게 되는가?
  • 측정은 스크립트, 판단은 모델. 정의에 "먼저 bash signals.sh <file> 를 실행하고 그 수치를 근거로 쓴다" 를 넣는다. 근거 수치가 항상 정확해지는 대신 룰의 허점(thin 변형)도 그대로 물려받는다. 어느 쪽이 나은가?
  • Bash 빼기. tools: Read, Write 로 바꾸고 size 샘플을 진단시킨다. 줄 수를 어떻게 말하는가? 근거 없는 판정이 늘어나는가?
  • 1층 비용 재기. .claude/skills/ 에 스킬을 10개 두고 /context 로 description 이 차지하는 토큰을 본다. 분리로는 줄지 않는 비용이 얼마인가?
  • 05-12 예고. 같은 샘플을 ex-05-12 의 antipattern-detector 에 넣어 본다. 크기 신호는 안티패턴 1 과 같은 기준(500줄)이고, 도메인 분기는 "references 부재 + 분기 ≥ 4" 로 더 엄격하다. domain 샘플(분기 3)은 어느 쪽에서 잡히는가?

토론

  1. 500줄이라는 숫자는 어디서 왔을까? 줄 수는 토큰의 좋은 대리 지표인가 — SQL 코드 블록 100줄과 산문 100줄은 같은 비용인가?
  2. 분기 헤딩이 3개인데 각 본문이 5줄이라면 나눠야 하는가? 분리에도 비용이 있다(파일 수, 라우팅 오류, Read 왕복). 신호와 비용을 어떻게 저울질할 것인가?
  3. 세 룰을 전부 스크립트로 잴 수 있다면 에이전트는 왜 필요한가? 에이전트만 할 수 있는 부분(권고문, nomarker 같은 표현 변형 인식)은 그 비용을 정당화하는가?
  4. 1층(description)은 스킬 수만큼 항상 실린다. 스킬이 30개면 description 만으로 얼마나 차지할까? "description 이 길다" 도 분리 신호가 될 수 있는가?
  5. 정의의 검증 루프는 "오차 1건이면 REDO" 라고만 한다. 오차를 누가, 무엇과 비교해 판정하는지 정의에 써넣는다면 어떤 문장이 되어야 하는가?

정리

  • 스킬은 세 층으로 로드된다. description 은 항상, 본문은 호출 시 전부, references 는 가리킬 때만. 분리는 2층을 3층으로 내리는 일이다.
  • 분리 신호는 크기 · 도메인 분기 · 조건부 상세 셋이고, 처방이 각각 다르다(목차화 · 메뉴판/레시피 · 조건부 링크).
  • "길다", "분기한다" 는 재현되지 않는다. 숫자와 패턴으로 바꿔야 스크립트로 잴 수 있고, 에이전트의 판정을 채점할 수 있다.
  • 진단 에이전트의 정확도는 신호를 하나씩 심은 샘플 + 대조군으로 잰다. 오탐과 누락을 따로 센다.
  • 기계 기준과 모델 판정이 갈리는 곳이 룰을 고칠 곳이다. 모델이 옳으면 룰에 조건을 더하고, 기계가 옳으면 정의를 더 좁힌다.
  • 진단기는 Edit 이 없다. 찾는 에이전트와 고치는 단계를 나누는 4장의 패턴이 스킬에도 그대로 적용된다.
