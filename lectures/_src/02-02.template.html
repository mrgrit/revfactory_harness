첫 하네스 — 2인 팀 커밋 메시지

이번에는 Claude 에게 하네스를 만들어 달라고 하지 않는다. 파일 4개를 직접 손으로 쓴다. 초안을 쓰는 commit-msg-author, 검증하는 commit-msg-reviewer, 둘을 순서대로 부르고 판정에 따라 되돌리는 commit-message 스킬. 이것이 책이 말하는 최소 하네스다.

⏱ 예상 40~50분 서브에이전트 정의스킬 정의생성–검증 루프MAX_RETRIES

학습 목표

  • 에이전트 정의 파일의 frontmatter 필드(name · description · model · tools)와 본문 구조(역할 · 원칙 · 입출력 프로토콜)를 직접 작성할 수 있다.
  • 스킬 SKILL.md 에 전제 조건 → 호출 순서 → 판정 분기 → 종료 조건을 담은 워크플로우를 쓸 수 있다.
  • 에이전트 사이의 인수인계를 파일(_workspace/)로 하는 이유를 설명할 수 있다.
  • 생성자–검증자 루프에 재시도 상한을 두는 이유와 상한 도달 시의 처리를 설계할 수 있다.

개념 — 최소 하네스의 네 조각

02-01 의 하네스는 에이전트 3 + 스킬 3 이었다. 이번 실습은 그것을 가장 작은 단위로 줄인다. 만드는 사람과 검사하는 사람, 그리고 둘을 부르는 절차. 여기에 프로젝트 규칙을 담은 CLAUDE.md 를 더하면 파일 4개다.

파일종류하는 일입력 → 출력
CLAUDE.md프로젝트 규칙커밋 형식, 중간 산출물 위치, 에이전트/스킬 위치 3줄—
.claude/agents/commit-msg-author.md에이전트 (생성자)스테이지된 diff 와 최근 로그를 읽고 Conventional Commits 초안 작성git diff --cached, git log → _workspace/commit-draft.md
.claude/agents/commit-msg-reviewer.md에이전트 (검증자)초안의 형식·사실 일치를 검사해 PASS/REDO 판정commit-draft.md, diff → _workspace/review-report.md
.claude/skills/commit-message/SKILL.md스킬 (오케스트레이터)전제 조건 확인 → author → reviewer → 판정 분기 → 최대 2회 재시도사용자 요청 → 최종 커밋 메시지
🔁
생성자–검증자 루프
author 가 만들고 reviewer 가 판정하고, REDO 면 수정 지시를 붙여 author 를 다시 부른다. 이 패턴은 이후 6장 PR 리뷰, 8장 안전장치(MAX_RETRIES), 11장 코드 리뷰 팀에서 규모만 키워 반복된다. 여기서 뼈대를 손에 익혀 두자.

워크플로우

파일 4개 직접 쓰기

아래 원문을 그대로 옮겨 적어도 되지만, 각 파일에서 "왜 이 줄이 있는가" 를 먼저 읽자. 하네스는 문법보다 의도가 중요하다.

① CLAUDE.md — 3줄이면 충분하다

{{FILE:exercises/ex-02-02-my-first-harness/CLAUDE.md}}

02-01 의 CLAUDE.md 보다 훨씬 짧다. 파이프라인 순서를 여기에 적지 않은 이유는 그 책임이 스킬에 있기 때문이다. CLAUDE.md 는 "어디에 무엇이 있고 무슨 형식을 쓰는가" 만 말한다.

② commit-msg-author.md — 생성자

{{FILE:exercises/ex-02-02-my-first-harness/.claude/agents/commit-msg-author.md}}
줄읽는 법
description: 에 "커밋 메시지", "commit message"Claude 가 이 에이전트를 언제 꺼낼지 판단하는 근거. 사람이 쓰는 표현을 그대로 넣는다.
tools: Bash, Read, Writediff 를 읽으려면 Bash, 초안을 쓰려면 Write. Edit 은 없다 — 기존 파일을 고칠 일이 없고, 소스 코드를 건드릴 가능성을 원천 차단한다.
"스타일이 혼재하면 최근 10개 중 다수결"애매한 상황의 결정 규칙을 미리 준다. 안 주면 매번 다른 선택을 한다.
"diff 에 없는 변경을 넣지 않는다 — 추측 금지"reviewer 가 검사할 사실 일치 기준과 짝을 이룬다. 생성자 원칙과 검증자 기준을 맞춰 두면 REDO 가 줄어든다.
입출력 프로토콜입력 명령, 출력 파일 경로, 출력 형식을 못 박는다. 다음 에이전트가 어디를 읽으면 되는지 보장하는 계약이다.
⚠️
frontmatter 구분선 뒤의 공백
원본 파일의 --- 줄 끝에 공백이 하나 붙어 있다. 파서에 따라 frontmatter 를 인식하지 못할 수 있으니, 직접 쓸 때는 --- 뒤에 아무것도 붙이지 말자. 파일을 저장한 뒤 세션에서 /agents 로 목록에 뜨는지 확인하면 된다.

③ commit-msg-reviewer.md — 검증자

{{FILE:exercises/ex-02-02-my-first-harness/.claude/agents/commit-msg-reviewer.md}}
줄읽는 법
"주관적 문장력이 아닌 객관적 기준만"검증자는 재현 가능한 판정을 내려야 한다. "문장이 어색하다" 는 REDO 사유가 될 수 없다.
"판정 불확실 시 PASS 보다 REDO — 오검보다 누락이 비싸다"검증자의 기본값을 명시한다. 어느 쪽 오류가 더 비싼지는 도메인마다 다르므로 반드시 적어 준다.
"2회 재생성 후에도 REDO 면 경고와 함께 PASS 로 종료"reviewer 도 상한을 안다. 스킬이 루프를 끊지 못하는 상황에 대한 이중 안전장치.
출력 형식에 "수정 지시 — author 가 바로 적용할 수 있게"REDO 는 판정이 아니라 다음 입력이다. 재호출 프롬프트에 그대로 들어간다.

④ commit-message/SKILL.md — 오케스트레이터

{{FILE:exercises/ex-02-02-my-first-harness/.claude/skills/commit-message/SKILL.md}}
줄읽는 법
description: 의 "반드시 사용 … 단, git commit -m 대체는 아니다"발동 조건과 비발동 조건을 함께 쓴다. 이미 메시지가 있는 커밋까지 가로채면 사용자를 방해한다.
allowed-tools: Bash Read Write스킬이 실행되는 동안 허용되는 도구. 에이전트의 tools 와 별개로 스킬 수준의 경계다.
1. git diff --cached --quiet 의 exit codeLLM 판단이 아니라 결정론적 게이트. 스테이지된 변경이 없으면 에이전트를 부르지도 않는다. 토큰도 시간도 아낀다.
2·3. "Agent 도구로 호출"스킬은 직접 일하지 않는다. 서브에이전트를 호출하고 파일로 결과를 받는다.
4·5. 판정 분기와 "최대 2회"루프의 탈출 조건. 상한 없는 생성–검증 루프는 반드시 어딘가에서 멈추지 않는다.
"자동 승인 한계 도달 — 수동 검토 권장"실패를 숨기지 않는다. 마지막 draft 를 경고와 함께 돌려주고 사람에게 넘긴다.

author 와 reviewer 나란히

commit-msg-authorcommit-msg-reviewer
역할생성검증
toolsBash, Read, WriteRead, Bash, Write
읽는 것diff, 최근 로그초안, diff
쓰는 것_workspace/commit-draft.md_workspace/review-report.md
기본 성향추측 금지, 다수결불확실하면 REDO
모르는 것reviewer 의 존재author 의 존재 (파일만 본다)

마지막 줄이 핵심이다. 두 에이전트는 서로를 모르고 파일만 주고받는다. 그래서 각각을 따로 테스트할 수 있고, 산출물이 디스크에 남아 사후 감사가 된다. 컨텍스트로 넘기면 둘 다 안 된다.

실행

원본 저장소에는 2026-05-27 실행 결과가 _workspace/ 에 남아 있다. README.md 하나를 새로 만들어 스테이지한 뒤 "커밋 메시지 만들어줘" 를 요청한 경우다.

USER커밋 메시지 만들어줘

스킬의 description 에 있는 문구와 일치하므로 commit-message 스킬이 발동한다. 슬래시로 /commit-message 를 직접 쳐도 같다.

author 산출물 — _workspace/commit-draft.md

{{FILE:exercises/ex-02-02-my-first-harness/_workspace/commit-draft.md}}

제목 한 줄(type(scope): subject), 빈 줄, 본문 한 줄. 프로토콜의 "첫 줄 제목, 빈 줄, 본문 3줄 이내" 를 그대로 따랐다. 변경이 README 신규 생성 1건뿐이니 docs(readme) 가 맞다.

reviewer 산출물 — _workspace/review-report.md

{{FILE:exercises/ex-02-02-my-first-harness/_workspace/review-report.md}}

판정 PASS. 검증 항목 5개(형식 · type · scope · subject · diff 사실 일치)를 표로 남겼다. reviewer 정의에는 "판정 · 사유 · 수정 지시" 세 항목만 요구했는데 표까지 만들었다 — 형식을 더 엄격히 고정하고 싶다면 프로토콜에 표 유무를 명시해야 한다.

✅
PASS 이후
스킬은 초안을 사용자에게 제시하고 끝난다. 실제 커밋은 사람이 한다: git commit -F _workspace/commit-draft.md. 커밋까지 자동으로 하지 않는 것도 설계다 — 되돌리기 어려운 동작은 하네스 밖에 둔다.

직접 해보기

  1. 프로젝트 준비 
    mkdir my-first-harness && cd my-first-harness && git init
mkdir -p .claude/agents .claude/skills/commit-message _workspace
printf '_workspace/\n' > .gitignore
    _workspace/ 를 gitignore 에 넣는 이유: 넣지 않으면 다음 실행에서 초안·리포트 파일 자체가 diff 에 섞여 들어간다.
  2. 파일 4개 작성 위 원문을 각각 CLAUDE.md, .claude/agents/commit-msg-author.md, .claude/agents/commit-msg-reviewer.md, .claude/skills/commit-message/SKILL.md 로 저장한다. 에이전트 파일의 첫 줄 --- 뒤에 공백이 없는지 확인.
  3. 인식 확인 
    claude
    세션에서 /agents 를 입력해 commit-msg-author, commit-msg-reviewer 가 보이는지, / 만 입력해 commit-message 스킬이 목록에 있는지 본다. 안 보이면 frontmatter 를 다시 확인한다.
  4. 전제 조건 실패 경로부터 아무것도 스테이지하지 않은 상태에서 커밋 메시지 만들어줘 를 요청한다. 에이전트를 부르지 않고 "먼저 git add" 안내로 끝나야 한다. 실패 경로를 먼저 확인하는 습관을 들이자.
  5. 정상 경로 
    echo "# my-first-harness" > README.md
git add README.md .gitignore
    다시 커밋 메시지 만들어줘. 끝나면 _workspace/ 의 두 파일을 열어 판정과 사유를 읽고, 마음에 들면 커밋한다: 
    git commit -F _workspace/commit-draft.md
  6. REDO 경로 유도 author 의 원칙에서 "제목은 72자 이하" 를 지우고, 여러 파일을 한꺼번에 스테이지한 뒤 다시 실행한다. 제목이 길어지거나 diff 에 없는 내용이 섞이면 reviewer 가 REDO 를 내는지, 수정 지시가 author 재호출에 반영되는지, 그리고 몇 번 만에 멈추는지 관찰한다.

변형 실험

  • 상한 바꾸기. SKILL.md 의 "최대 2회" 를 0회로 바꾸면 무엇이 달라지나? 5회로 바꾸면 비용은 얼마나 늘고 품질은 얼마나 나아지나?
  • 검증자 성향 뒤집기. reviewer 의 "불확실하면 REDO" 를 "불확실하면 PASS" 로 바꾸고 같은 diff 로 여러 번 돌려 판정 분포를 비교한다.
  • 도구 빼 보기. reviewer 에서 Bash 를 빼면 diff 를 못 본다. 그래도 판정을 내리는가? 무엇을 근거로?
  • 영어 스타일 저장소. 최근 커밋이 영어인 저장소에서 실행해 "다수결" 원칙이 실제로 작동하는지 확인한다.

토론

  1. author 와 reviewer 를 한 에이전트로 합쳐 "쓰고 스스로 검토하라" 고 하면 무엇을 잃는가?
  2. 인수인계를 파일 대신 대화 컨텍스트로 하면 어떤 문제가 생기는가? (감사 가능성, 컨텍스트 오염, 개별 테스트)
  3. 재시도 상한 2회는 어디서 온 숫자인가? 이 도메인에서 적절한 근거를 대 보자.
  4. 스킬 description 의 "단, git commit -m 대체는 아니다" 가 없다면 어떤 오발동이 생길 수 있나?

정리

  • 최소 하네스 = 생성자 + 검증자 + 오케스트레이터(스킬) + 규칙(CLAUDE.md). 파일 4개, 100줄 남짓.
  • 에이전트 정의의 세 기둥은 description(발동 조건) · tools(경계) · 입출력 프로토콜(계약)이다.
  • 에이전트는 서로를 모르고 파일로만 소통한다. 그래야 따로 테스트되고 사후 감사가 된다.
  • 루프에는 결정론적 전제 조건과 재시도 상한이 있어야 한다. 상한에 닿으면 숨기지 말고 경고와 함께 사람에게 넘긴다.
