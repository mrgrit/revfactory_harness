학습 목표

  • 하네스가 무엇인지 — CLAUDE.md · .claude/agents/ · .claude/skills/ 세 요소로 설명할 수 있다.
  • 같은 프롬프트로 하네스 유무 A/B 실험을 내 환경에서 재현할 수 있다.
  • 산출물을 구조 · 출처 · 예시 · 재사용성 네 관점으로 비교하고 차이의 원인을 하네스 파일에서 짚어낼 수 있다.
  • 에이전트 정의 파일의 frontmatter(name / description / tools / model)를 읽고 "왜 이 도구만 줬는지" 말할 수 있다.

개념 — "대화를 잘 굴리기" vs "환경을 미리 세팅하기"

Claude Code 를 쓰는 방식은 크게 둘로 나뉜다. 하나는 매번 대화창에서 원하는 결과가 나올 때까지 프롬프트를 다듬는 방식이고, 다른 하나는 작업 전에 역할·절차·규약을 파일로 깔아 두고 짧은 요청만 던지는 방식이다. 후자에서 미리 깔아 두는 파일 묶음이 하네스(harness)다.

구성 요소위치역할이번 실습에서
CLAUDE.md프로젝트 루트세션 시작 시 자동 로드되는 프로젝트 규칙. 목적·폴더 구조·작업 흐름·원칙을 적어 두고 에이전트/스킬을 가리키는 포인터 역할3 에이전트 파이프라인 순서와 "추측 금지" 같은 원칙을 명시
서브에이전트.claude/agents/*.md독립된 컨텍스트에서 특정 역할만 수행하는 전문가. frontmatter 로 tools·model 을 제한할 수 있다tip-researcher · tip-writer · tip-curator
스킬.claude/skills/<name>/SKILL.md에이전트들이 공유하는 절차·규약. "어떤 순서로, 어떤 형식으로" 를 한 곳에 고정한다tip-collect · tip-format · tip-publish
💡
핵심 질문
프롬프트를 아주 길고 자세하게 쓰면 하네스 없이도 같은 결과를 얻을 수 있지 않을까? 실습이 끝난 뒤 토론에서 이 질문으로 돌아온다. 힌트는 재사용성과 강제력이다.

# Claude Code 사용 팁

## 효율적인 프롬프트

- **구체적으로 작성**: "버그 고쳐줘"보다 `auth.ts:42`에서 토큰 만료 처리 버그처럼 파일/라인을 지정
- **컨텍스트 제공**: 이미 시도한 것, 제약사항을 먼저 알려주기
- **병렬 처리**: 독립적인 작업은 한 메시지에 묶어서 요청

## 핵심 단축 명령

| 명령 | 설명 |
|---|---|
| `!<command>` | 쉘 명령 직접 실행 (결과가 대화에 포함됨) |
| `/<skill>` | 스킬 호출 (예: `/commit`, `/simplify`) |
| `/help` | 도움말 |
| `/fast` | 빠른 출력 모드 토글 |

## 파일 & 메모리

- **CLAUDE.md**: 프로젝트 루트에 두면 자동 로딩 — 규칙/컨벤션 명시
- **메모리 시스템**: "기억해줘"라고 하면 영구 저장, 다음 세션에서도 유지
- **피드백 저장**: 교정해주면 같은 실수를 반복하지 않음

## 서브에이전트 활용

- **Explore**: 코드베이스 광범위 탐색 (여러 쿼리가 필요할 때)
- **Plan**: 복잡한 구현 전략 설계
- **general-purpose**: 멀티스텝 리서치
- 독립적인 작업은 **병렬로** 여러 에이전트 동시 실행

## 도구 선택

- 파일 검색은 **Glob**, 내용 검색은 **Grep** (bash의 `find`/`grep` 대신)
- 읽기는 **Read**, 편집은 **Edit** — 전용 도구가 리뷰에 유리

## 안전한 작업

> ⚠️ 파괴적 작업(`push --force`, `rm -rf`, `reset --hard`)은 먼저 확인

- `--no-verify`로 훅 건너뛰지 않기 — 근본 원인을 수정
- 커밋은 **명시적으로 요청할 때만**

## 플랜 모드

- 큰 변경 전 `EnterPlanMode`로 계획을 먼저 승인받기
- 중간에 접근이 바뀌면 플랜 업데이트

## 확장 통합

- **IDE 확장**: VS Code, JetBrains 지원
- **MCP 서버**: Chrome 브라우저 자동화, Google Workspace 등
- **스케줄링**: `/schedule`로 cron 작업 등록
- **훅(hooks)**: `settings.json`에 등록해 자동화 트리거

## 워크트리

- `isolation: "worktree"`로 격리된 브랜치에서 실험 — 원본에 영향 없음

## 팁 오브 팁

1. 에이전트에겐 **"왜"까지 설명** — 단순 명령보다 맥락이 결과 품질을 좌우
2. 응답 길게 원치 않으면 **"간결히"**, **"200자 이내"** 명시
3. 이슈/PR 참조는 `owner/repo#123` 형식으로 클릭 가능

하네스 구성 (B-1)

두 번째 폴더에서는 팁을 정리하기 전에 하네스부터 만든다. 원본 저장소 README 는 /harness:harness 메타 스킬을 언급하지만, 스크린샷의 실제 입력은 아래와 같은 자연어 요청이다. 어느 쪽이든 결과 구조는 같다.

USERclaude code 사용 팁 정리하려고 합니다. 사용팁 정리를 위한 Agent들과 Agent 가 사용할 스킬을 현재 폴더 하위의 .claude 에 구성합니다. 현재 폴더에 관련 내용으로 Claude.md 파일을 작성합니다.

에이전트 3종 — 도구 경계가 곧 역할

세 파일의 frontmatter 만 나란히 놓아도 설계 의도가 보인다. 리서처는 쓰지 못하고, 라이터는 검색하지 못한다.

에이전트toolsmodel사용하는 스킬이렇게 제한한 이유

tip-curatorRead, Write, Edit, Glob, Grep, Bashsonnettip-publish전체 폴더를 훑어 중복·누락을 잡고 인덱스를 다시 쓴다. 정렬·검사에 Bash 가 유용

---
name: tip-researcher
description: Claude Code 사용 팁의 소재를 리서치하는 전문 에이전트. 공식 문서, 릴리즈 노트, 설정 파일, 훅/MCP/스킬 구조 등을 조사해 팁 후보를 수집한다. 사용자가 "Claude Code 팁 찾아줘", "이 기능 관련 팁 조사"처럼 요청할 때 사용.
tools: Read, Glob, Grep, WebFetch, WebSearch, Bash

---

당신은 Claude Code 사용 팁을 발굴하는 리서처입니다.

## 역할
- 사용자가 제시한 주제(예: 훅, 슬래시 커맨드, MCP, 서브에이전트, 스킬, 설정, 키바인딩)에 대해 실전에 바로 쓸 수 있는 팁 후보를 모은다.
- 공식 문서(docs.claude.com/claude-code), GitHub 저장소(anthropics/claude-code), 사용자의 `~/.claude/` 설정을 우선 소스로 삼는다.

## 절차
1. `tip-collect` 스킬의 지침에 따라 소스를 정한다.
2. 각 후보에 대해: 제목(한글), 한 줄 요약, 출처, 검증 방법을 메모한다.
3. 중복·추측성 내용은 제외한다. 확인 가능한 것만 올린다.
4. 결과는 Markdown 체크리스트로 돌려준다 — `tip-writer`가 바로 집어 쓸 수 있는 형태로.

## 출력 형식
```
## 주제: <주제명>
- [ ] <팁 제목> — <한 줄 요약> (출처: <URL/경로>)
```

## 글쓰기 원칙
- 한국어, 존댓말이 아닌 간결한 설명체("~한다").
- 구조: 상황 → 방법 → 예시(코드/명령) → 주의점.
- 한 파일 = 한 팁. 파일명은 `kebab-case.md`.
- 추측 금지. 확인 불가능한 내용은 빼거나 "확인 필요"로 표시.
- 예시 코드는 복사 후 바로 쓸 수 있도록.

## 산출물

- 작성 후 파일 경로와 한 줄 요약을 응답으로 돌려준다.

# tip-collect

Claude Code 팁 소재 수집 표준 절차.

## 소스 우선순위
1. **공식 문서**: https://docs.claude.com/claude-code (features, hooks, slash-commands, mcp, skills, settings, subagents)
2. **공식 저장소**: https://github.com/anthropics/claude-code (릴리즈 노트, 이슈, CHANGELOG)
3. **사용자 설정**: `~/.claude/` (settings.json, agents/, skills/, commands/)
4. **세션 관찰**: 현재 대화에서 드러난 기능/에러/도구 목록

## 수집 단계
1. 주제 확정 — 예: "훅", "서브에이전트", "MCP"
2. 위 소스에서 관련 키워드 검색 (WebFetch/WebSearch/Grep)
3. 각 후보마다 다음 4가지를 메모:
   - **제목(한글)**
   - **한 줄 요약**
   - **출처 URL 또는 파일 경로**
   - **검증 방법** (실행해볼 명령/설정)
4. 중복 제거 — 이미 `tips/`에 있는 항목은 제외 (Grep으로 체크)
5. 추측·미검증 내용 제외

## 출력
Markdown 체크리스트:
```
## 주제: <주제>
- [ ] <제목> — <요약> (출처: <링크>)
```
.claude/skills/tip-format/SKILL.md — 문서 표준 포맷 
---
name: tip-format
description: tips/ 하위 팁 문서의 표준 포맷과 프론트매터 규약. 새 팁 문서 작성 시 반드시 이 포맷을 따른다.
---

# tip-format

Claude Code 팁 문서의 표준 포맷.

## 파일 위치/이름
- 경로: `tips/<kebab-case>.md`
- 이름: 영문 소문자 + 하이픈 (예: `hooks-pre-tool-use.md`)

## 프론트매터 (필수)

# tip-publish

팁 문서 발행/인덱싱 절차.

## 단계
1. `tip-format` 규약 준수 여부 확인 (프론트매터, 본문 구조).
2. 파일을 `tips/<kebab-case>.md`로 저장.
3. `tips/README.md`를 갱신:
   - 태그/카테고리별 섹션 유지
   - 항목 포맷: `- [<제목>](<파일명>.md) — <한 줄 요약>`
   - 알파벳/업데이트일 기준 정렬
4. 같은 주제 기존 파일이 있으면 **Edit로 병합**하고 `updated` 갱신. 새 파일을 중복 생성하지 않는다.
5. 변경 요약을 응답으로 돌려준다.

# Claude Code 사용 팁 정리 프로젝트

이 저장소는 Claude Code(공식 CLI)의 실전 사용 팁을 수집·정리·발행하기 위한 작업 공간입니다.

## 목적
- Claude Code의 기능(훅, 슬래시 커맨드, MCP, 서브에이전트, 스킬, 설정 등)에 대한 팁을 한국어로 정리한다.
- 팁은 `tips/` 폴더 아래에 주제별 Markdown 파일로 축적한다.
- 정리 작업은 전용 서브에이전트와 스킬이 분담한다.

## 폴더 구조
- `tips/` — 정리된 팁 문서(주제별 `.md`)
- `.claude/agents/` — 팁 작업 전용 서브에이전트
  - `tip-researcher` — 공식 문서/릴리즈노트/코드베이스에서 팁 소재 리서치
  - `tip-writer` — 리서치 결과를 사용자 친화적 한국어 팁 문서로 작성
  - `tip-curator` — 기존 `tips/` 중복·품질 점검 및 인덱스(README) 갱신
- `.claude/skills/` — 위 에이전트들이 공통으로 쓰는 스킬
  - `tip-collect` — 소스에서 팁 소재를 모으는 절차
  - `tip-format` — 팁 문서 표준 포맷/프론트매터 규약
  - `tip-publish` — `tips/`에 저장하고 인덱스 갱신하는 절차

## 작업 흐름
1. 사용자가 주제를 제시하거나 "팁 정리" 요청을 한다.
2. `tip-researcher` 에이전트가 `tip-collect` 스킬을 사용해 소재를 수집한다.
3. `tip-writer` 에이전트가 `tip-format` 스킬 규약에 맞춰 초안을 작성한다.
4. `tip-curator` 에이전트가 `tip-publish` 스킬로 `tips/`에 저장하고 `tips/README.md` 인덱스를 갱신한다.

## 원칙
- 한국어로 작성, 커밋 메시지도 한국어.
- 팁 하나 = 한 파일. 파일명은 `kebab-case.md`.
- 추측 금지, 검증 가능한 공식 소스 또는 직접 실험 결과만 수록.
- 각 팁은 "상황 → 방법 → 예시 → 주의점" 순서를 권장.

# PostToolUse 훅으로 파일 저장 시 자동 린트 실행

## 상황

Claude가 Edit/Write/MultiEdit 툴로 파일을 수정할 때마다 수동으로 린터를 돌려야 하는 번거로움이 있다. 코드 품질 체크를 자동화하고 싶다.

## 방법

1. `.claude/settings.json`의 `hooks` 항목에 `PostToolUse` 훅을 추가한다.
2. `matcher`를 `"Write|Edit|MultiEdit"`으로 설정해 파일 수정 툴만 걸러낸다.
3. stdin으로 전달되는 JSON에서 `tool_input.file_path`를 읽어 해당 파일에만 린터를 실행하는 스크립트를 작성한다.

## 예시

`.claude/settings.json`:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit|MultiEdit",
        "hooks": [
          {
            "type": "command",
            "command": "bash .claude/scripts/lint-on-save.sh"
          }
        ]
      }
    ]
  }
}
```

`.claude/scripts/lint-on-save.sh`:

```bash
#!/usr/bin/env bash
# stdin에서 tool_input.file_path 추출
FILE_PATH=$(cat - | python3 -c "import sys,json; d=json.load(sys.stdin); print(d.get('tool_input',{}).get('file_path',''))")

if [ -z "$FILE_PATH" ]; then
  exit 0
fi

# 확장자에 따라 린터 선택
case "$FILE_PATH" in
  *.py) python3 -m ruff check "$FILE_PATH" ;;
  *.ts|*.tsx|*.js|*.jsx) npx eslint "$FILE_PATH" ;;
  *.go) golint "$FILE_PATH" ;;
esac
```

## 주의점

- `PostToolUse` 훅은 툴 실행을 **차단할 수 없다**. 사전 차단이 필요하면 `PreToolUse` 훅을 사용한다.
- 스크립트가 비정상 종료해도 Claude의 작업 흐름은 계속된다. 린트 오류를 Claude에게 알리려면 훅 출력을 활용하거나 별도 피드백 메커니즘을 설계해야 한다.
- `matcher`는 정규식이므로 `"Write|Edit|MultiEdit"` 외에 세밀한 패턴도 지정할 수 있다.

전체 산출물은 원본 저장소의 2단 비교 페이지에서 나란히 볼 수 있다.

  • 2단 비교 페이지 열기 (index.html)
  • A 산출물 원문 · B 산출물 합본 원문 · B 인덱스

직접 해보기

아래 순서대로 내 환경에서 재현한다. 두 세션을 나란히 띄우면 차이가 실시간으로 보인다.

  1. 폴더 준비 
    mkdir -p harness-abtest/non-harness harness-abtest/apply-harness
cd harness-abtest
  2. A — 맨몸 실행 
    cd non-harness && claude

  3. B-1 — 하네스 구성 
    cd ../apply-harness && claude
    위 하네스 구성 프롬프트를 입력한다. 권한 질문에는 "Yes, and always allow access to .claude/ from this project" 를 고르면 이후 질문이 줄어든다. 끝나면 확인: 
    find .claude -type f
cat CLAUDE.md
    에이전트가 인식됐는지는 세션 안에서 /agents 로 볼 수 있다.
  4. B-2 — 하네스 실행 Ctrl+C 두 번으로 세션을 끝내고 claude 를 다시 띄운다(CLAUDE.md 는 세션 시작 시 로드된다). A 와 같은 문장 claude code 사용 팁 정리해주세요. 를 입력하고, 파이프라인이 자동으로 발동하는지 본다. 발동하지 않으면 "CLAUDE.md 의 작업 흐름대로 진행해 주세요" 를 덧붙인다.
  5. 비교 아래 체크리스트로 두 산출물을 채점한다.
    • 팁 하나가 파일 하나인가
    • 모든 팁이 같은 섹션 구조를 따르는가
    • 각 팁에 출처 URL 이 있는가
    • 예시 설정/명령을 그대로 복사해 쓸 수 있는가
    • 인덱스(README)가 있고 다음 실행에서 누적되는 구조인가

시간과 비용
B-2 는 원본 기준 7분, 토큰 86k 이상을 쓴다. 강의 시간이 빠듯하면 tip-researcher.md 의 절차에 "후보는 3개까지" 를 추가해 규모를 줄인 뒤 돌려 보자. 하네스는 파일을 고쳐서 행동을 바꾸는 것이므로, 이것 자체가 좋은 연습이다.

토론

  1. 긴 프롬프트 vs 하네스. tip-format 의 내용을 통째로 프롬프트에 붙여 넣으면 B 와 같은 결과가 나올까? 나온다면, 하네스가 여전히 유리한 점은 무엇인가? (다음 주에 같은 요청을 할 때를 생각해 보자.)
  2. 도구 경계. tip-writer 에 WebSearch 를 주면 무엇이 달라질까? 반대로 tip-researcher 에 Write 를 주면?
  3. 실험의 한계. 이 비교는 N=1 이고 B 의 프롬프트가 미묘하게 다르다. 더 공정한 비교를 위해 무엇을 통제해야 하나? (5장 05-11 With/Without 에서 정량 비교로 이어진다.)
  4. 비용. 7분·86k 토큰이 "비싸다" 고 느껴지는가? 어떤 작업이라면 이 투자가 정당화되는가?

정리

  • 하네스 = CLAUDE.md(포인터) + 에이전트(역할·도구 경계) + 스킬(절차·규약). 요청 문장은 짧아지고 결과는 구조화된다.
  • 산출물 차이의 원인은 매번 특정 파일의 특정 줄로 추적된다. 포맷은 tip-format, 출처는 tip-collect, 누적은 tip-publish.
  • 서브에이전트의 tools 제한은 권한 문제이자 품질 장치다. 검색 못 하는 라이터는 지어내지 못하고, 쓰지 못하는 리서처는 초안을 문서로 굳히지 못한다.
  • 비용은 리서처에 몰린다. 무거운 컨텍스트를 서브에이전트에 격리하는 것이 메인 세션을 가볍게 유지하는 방법이다.
